## О проекте

**SzBot** — двуязычный Telegram-бот, который представляет портфолио разработчика и превращает интерес потенциального клиента в заявку. Пользователь просматривает информацию о разработчике и проектах, выбирает язык и отправляет описание задачи. Бот сохраняет заявку в SQLite и уведомляет администратора.

Проект демонстрирует практическую интеграцию Telegram Bot API на **aiogram 3**, маршрутизацию событий, диалоговое состояние и сохранение лидов. Текущая реализация — компактный прототип; ограничения и направления развития архитектуры описаны ниже.

## Возможности

- Русский и английский интерфейс.
- Разделы портфолио: информация о разработчике, проекты, контакты и отзывы.
- Форма заявки на основе FSM: ввод свободного текста и возможность отмены.
- Сохранение заявок с идентификатором пользователя, текстом, статусом и временем создания.
- Уведомление администратора о новой заявке.
- Команда администратора `/orders` для просмотра активных заявок и callback-действие для отметки заявки выполненной.

## Технологии и архитектурные подходы

| Область | Реализация |
|---|---|
| Runtime | Python 3.10+ |
| Telegram API | aiogram 3.x: `Bot`, `Dispatcher`, `Router`, фильтры и обработчики |
| Диалоги | FSM aiogram с хранением выбранного языка и состояния формы заявки |
| Хранилище | SQLite через стандартный модуль `sqlite3`; схема создаётся при запуске |
| Конфигурация | Переменные окружения из `.env`, загружаемые `python-dotenv` |
| Интеграции | PyGithub указан в зависимостях; показ активности GitHub в меню отключён |

### Архитектурные свойства

- **Event-driven routing**: обработчики сгруппированы по `Router` и подключаются к `Dispatcher`.
- **FSM**: диалоговое состояние хранит контекст взаимодействия пользователя между событиями Telegram.
- **Separation of concerns (частично)**: обработка Telegram-событий находится в `handlers/`, SQL-запросы — в `database.py`, создание клавиатур — в `keyboards.py`.
- **Data access boundary**: функции в `database.py` отделяют SQL-операции от обработчиков. Это основа для Repository Pattern, но полноценного слоя репозиториев и бизнес-сервисов в текущей версии нет.
- **Dependency injection aiogram**: `Bot` и `FSMContext` передаются обработчикам средствами aiogram. Отдельный контейнер приложения и внедрение сервисов не настроены.
- **Async handlers**: Telegram-обработчики объявлены асинхронными. При этом операции SQLite используют синхронный `sqlite3` и блокируют event loop на время выполнения; это следует учитывать перед ростом нагрузки.

## Запуск

### Требования

- Python 3.10 или новее.
- Telegram-бот, созданный через [@BotFather](https://t.me/BotFather).

### 1. Клонирование и виртуальное окружение

```bash
git clone https://github.com/ZeroStalker3/SzBot.git
cd SzBot
python -m venv .venv
```

Активируйте окружение:

```bash
# Linux / macOS
source .venv/bin/activate

# Windows PowerShell
.venv\Scripts\Activate.ps1
```

### 2. Установка зависимостей

```bash
python -m pip install -r requirements.txt
```

### 3. Конфигурация окружения

Создайте `.env` в корне проекта. Файл `.env` не следует добавлять в Git.

```dotenv
BOT_TOKEN=полученный_токен_бота
ADMIN_ID=123456789
PROXY_URL=
```

`BOT_TOKEN` и `ADMIN_ID` необходимы для работы приложения. `ADMIN_ID` — числовой Telegram ID администратора. `PROXY_URL` необязателен и используется при подключении через прокси.

В текущем коде значения читаются в [config.py](./config.py) через `python-dotenv`; типизированной валидации `pydantic-settings` пока нет. Для production-конфигурации рекомендуется заменить чтение переменных на `pydantic-settings`, задать типы и обязательность настроек и завершать запуск с понятной ошибкой при некорректной конфигурации. Не храните токены в исходном коде или примерах конфигурации.

### 4. Инициализация базы и запуск

При старте `bot.py` вызывает `init_db()`: если таблицы `orders` ещё нет, она создаётся в SQLite-файле `orders.db`.

```bash
python bot.py
```

Бот запускается в режиме long polling. Отдельной команды для миграций в текущем проекте нет. `CREATE TABLE IF NOT EXISTS` обеспечивает только первичное создание схемы; для версионирования изменений схемы и безопасных обновлений существующей базы рекомендуется внедрить Alembic.

## Команды и пользовательские сценарии

### Команды

| Команда | Доступ | Поведение |
|---|---|---|
| `/start` | Все пользователи | Предлагает выбрать язык, затем показывает главное меню |
| `/orders` | Администратор | Выводит активные заявки; обработчик проверяет Telegram ID по `ADMIN_ID` |

### Callback-сценарии

| Сценарий | Router / callback | Результат |
|---|---|---|
| Выбор языка | `start` / `lang_ru`, `lang_en` | Сохраняет `language` в контексте FSM и открывает меню |
| Навигация по портфолио | `menu` / `info`, `projects`, `contacts`, `reviews`, `back` | Показывает соответствующий раздел |
| Создание заявки | `order` / `order` → FSM `waiting_for_order` | Принимает текст, сохраняет заявку в SQLite и отправляет уведомление администратору |
| Отмена заявки | `order` / `cancel_order` | Очищает диалог и возвращает пользователя в меню |
| Работа с заявками | `order` / `complete_<id>` | Меняет статус заявки на `completed` |

Форма заявки сейчас **одношаговая**: пользователь вводит произвольное описание задачи. Состояния `waiting_for_service`, `waiting_for_budget`, `waiting_for_description` и `confirm_order` не реализованы.

## Структура проекта

Фактическая структура текущей версии небольшая и плоская:

```text
SzBot/
├── bot.py                 # Инициализация Bot/Dispatcher, регистрация роутеров, polling
├── config.py              # Чтение конфигурации из окружения
├── database.py            # Инициализация SQLite и функции доступа к заявкам
├── handlers/
│   ├── start.py           # Команда /start и выбор языка
│   ├── menu.py            # Разделы портфолио и навигация
│   └── order.py           # FSM формы заявки и обработчики заявок
├── keyboards.py           # Inline-клавиатуры
├── states.py              # Группы состояний FSM
├── utils.py               # Вспомогательные функции и проверка администратора
├── requirements.txt
├── orders.db              # SQLite-база, создаваемая при работе приложения
└── LICENSE
```

### Целевая структура для развития

При добавлении новых сценариев приложение можно разделить на слои без привязки бизнес-логики к Telegram API:

```text
src/
├── main.py
├── core/
│   ├── config.py          # Pydantic Settings, переменные окружения
│   ├── logging.py         # Настройка логирования
│   └── container.py       # Сборка зависимостей приложения
├── handlers/
│   ├── user/              # Пользовательские aiogram routers
│   └── admin/             # Административные aiogram routers
├── middlewares/           # Корреляция, контекст и обработка сквозных concerns
├── states/                # FSM-состояния Telegram-сценариев
├── services/              # Бизнес-правила и прикладные сценарии
├── repositories/          # Интерфейсы и реализации доступа к данным
├── infrastructure/
│   └── database/          # Подключение, модели и транзакции
└── keyboards/             # Построение Telegram-клавиатур

alembic/                   # Версионируемые миграции схемы БД
```

`handlers` отвечают за Telegram-ввод/вывод и делегируют действия сервисам; `services` реализуют бизнес-сценарии; `repositories` скрывают детали хранения; `infrastructure` содержит конкретные адаптеры; `core` отвечает за конфигурацию и сборку приложения. Такая граница упрощает тестирование сервисов и замену SQLite на PostgreSQL без переноса SQL-логики в обработчики.

Эта структура — **целевой вариант**, а не описание уже существующих каталогов. В текущем проекте нет `services/`, `repositories/`, `middlewares/`, Pydantic Settings, Alembic и ORM.

## Production-развитие

Перед эксплуатацией под существенной нагрузкой рекомендуется:

1. Перевести SQLite-операции на асинхронный драйвер либо выносить синхронные операции из event loop; при нескольких экземплярах бота рассмотреть PostgreSQL.
2. Ввести `pydantic-settings` для типизированной конфигурации и централизованной валидации обязательных переменных окружения.
3. Вынести бизнес-логику из обработчиков в сервисный слой и обращаться к данным через репозитории.
4. Добавить Alembic-миграции, тесты для сервисов и FSM-сценариев, структурированные логи и мониторинг ошибок.
5. Проверить авторизацию каждого административного callback-действия, а не только команды `/orders`.
6. Определить политику хранения персональных данных заявителей, резервного копирования и ротации секретов.

### Docker (опционально)

В репозитории пока нет `Dockerfile` и `compose.yaml`, поэтому контейнерный запуск сейчас не настроен. При добавлении контейнеризации передавайте `BOT_TOKEN`, `ADMIN_ID` и остальные секреты через окружение или secret manager, а файл SQLite подключайте как постоянный volume. Не встраивайте `.env` с секретами в образ.
